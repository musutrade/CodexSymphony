# Repository instructions

## Temporary Rust closure convention

Until the approved source collector has verified complete closure support:

- Do not introduce closures in production Rust code, including `|...|`, `move |...|`, and async closures. When editing a production function, replace its closures with equivalent explicit control flow or ordinary named functions.
- Existing, unchanged production functions are outside this migration requirement. Do not rewrite the repository in bulk. Test-only code may use closures; keep production logic in the measured production inventory.
- Preserve behavior, error propagation, short-circuiting, ordering and authority boundaries. Do not move logic into macros, generated code, excluded files or test code to evade measurement.
- Refactor complex code into cohesive named functions and add meaningful tests as needed. CRAP must remain <= 10, required coverage remains unchanged, and missing or unsupported measurements remain failures. Do not add exclusions, claim N/A, infer closure counts from parent execution, or reuse another source's evidence.
- Source-inventory compatibility is only a preliminary check. Changed code must produce exact source-bound LLVM coverage/CRAP measurements and pass the complete Gate on the final exact tree before publication.

This temporary convention addresses observed rc.7 mapping gaps; it does not assert that all closures fail or that ordinary Rust compilation is unsupported. Remove it only after a reviewed collector upgrade passes retained regression cases for field-projection closures, unit-return closures, macro-bodied closures, captures, async closures, and generic monomorphizations, with exact counters and source-bound measurements, followed by a complete Gate PASS. A version change alone does not lift the rule.

## Validation order for all code

For every code change, run the approved source-bound coverage and CRAP measurements first. Run other tests only after both measurements pass. Missing, unavailable, or unsupported measurements are failures; do not skip them, claim N/A, or substitute measurements from another source. Complete the required Gate on the final exact tree before publication.

## Development procedure (single source of truth)

Read this section at task start, after resuming a task, and before validation or publication. It defines the development sequence for both interactive Codex work and Symphony-controlled work. Other prompts and developer guides must link here rather than maintain their own sequence. Task-specific acceptance requirements are additional requirements, not replacements for this procedure.

Resolve operational values from their existing authorities; do not copy today's versions, digests, thresholds, commands or CI event assumptions into a new checklist:

| Concern | Authority |
| --- | --- |
| Runtime, dependencies and collectors | `environment.lock.json`, toolchain/version locks, dependency lockfiles and the matching installed host approval |
| Required checks and command arguments | `.harness-gate/flow.toml`, checked-in package scripts and task acceptance criteria |
| Measurement scope and quality policy | `.harness-gate/quality.toml`, `.harness-gate/packs/` and matching host approval |
| Source-bound publication admission | Installed publication host; repository implementation in `tools/publication/gate.py` |
| CI triggers and remote acceptance | `.github/workflows/quality.yml`, installed remote host and current branch protection |
| Real task resources and recovery | Original Requirement account and authorization ledger, deployed per-call reservations, `docs/budgets.md` |

A disagreement with installed approval is a concrete prerequisite failure. Do not repair it by silently changing locks, approving new tools, weakening policy or treating an old document as authority. This procedure changes development orchestration; it does not authorize modifying the internals of an approved host.

### Required stages and transitions

1. **Establish scope and prerequisites.** Record the task, acceptance criteria, baseline, branch and workspace. Preserve unrelated dirty work. Check the actual pinned tools, dependencies, isolated test database, capacity and authorized runner readiness before expensive execution. Read-only environment and source-inventory checks do not establish quality PASS and must not become ordinary tests before measurements pass.

   For real model acceptance, reconcile the cumulative task limit and per-call reservation with retained usage from the actual Runtime. Input includes context and cached input; do not add or subtract cached input again when checking token limits. Unknown usage retains its reservation. A budget stop requires the original account's explicit increase authorization and normal recovery; neither a new Requirement nor a restarted process resets paid work or unresolved exposure.
2. **Check the validation checkout.** Before a full Gate, establish that Git metadata and required inputs are accessible from the approved execution environment. A linked worktree whose `.git` points outside that environment is not sufficient. Use a standalone clone for validation when needed, transfer all intended additions, deletions and file modes, and verify its exact source tree against the development tree. Do not wait for a long capture to discover an inaccessible Git directory, or copy only tracked modifications and lose new files.
3. **Implement and measure.** Apply the repository formatter as an editing operation before freezing capture inputs; this does not establish a test or quality PASS. Run format verification in stage 4. Use the approved source inventory to screen changed production functions for unsupported constructs and complexity already above the policy CRAP ceiling before scheduling a full capture; this is preliminary screening, never measurement PASS. Use the temporary Rust convention above. While the approved collector cannot distinguish inline test subjects, keep new test-only Rust modules in the established external `tests/unit` layout, referenced through `cfg(test)` and `path`; production logic stays in the measured inventory. Obtain approved exact source-bound coverage and CRAP results, resolving unsupported sources and failures before proceeding. A successful inventory or capture command alone is not a passing measurement. The tests required to produce measurements belong to this stage.
4. **Run checks after measurement PASS.** Run the applicable format, Clippy, frontend lint/build, ordinary tests and acceptance checks using the authoritative configuration. In particular, run Clippy and the configured secret scan on the measured candidate before starting an expensive complete Gate. Test credentials must use explicit placeholders already recognized by the existing scan policy; do not add an exemption to make a fixture pass. After a code change, return to stage 3; an earlier measurement does not authorize tests of changed code. Preserve exact-source evidence and avoid repeating successful checks without a new change, failure or unresolved requirement.
5. **Complete any independently bound acceptance.** If task acceptance requires a separately authorized runner, establish readiness in stage 1. After stages 3–4, use a complete local Gate as a diagnostic if that acceptance protocol requires it; then request the final exact-source runner binding and real acceptance. Do not request new bindings for every intermediate edit. A diagnostic PASS does not replace real acceptance. Finish that acceptance and its evidence before the final publication Gate.
6. **Freeze and run the final complete Gate.** Finalize all source, documentation and tracked evidence first. Record the exact source tree, environment and approval identity; run the installed approved complete Gate on that candidate. Require PASS, complete evidence and the retained report identity. Any subsequent change to an input bound by the receipt invalidates that receipt: reconcile the change, remeasure changed code, rerun affected checks and obtain a new final exact-tree Gate PASS. Source-bound admission remains required even for changes that look harmless. Do not use a partial hook, unsigned diagnostic, another tree's report or a receipt from an earlier environment as publication authority.
7. **Publish and establish CI, when authorized.** Recheck that the publication tree equals the validated tree and use the designated publication channel. Read back the remote commit/tree. Create or reuse the PR promptly within the authorized delivery scope; inspect current workflow triggers instead of assuming a feature-branch push starts CI. If an appropriate run already exists for the exact PR head, do not add a duplicate manual run. Enable auto-merge when authorized and let required checks govern it; never bypass protection. If authorized scope ends at local edits, stop there and state that publication has not occurred.
8. **Hand off or wait as requested.** Report the actual commit/PR, validation evidence, pending checks and remaining acceptance limits. CI success or merge alone is not product acceptance. Symphony delegates CI waiting to its controller. In interactive work, if the user will notify you, stop polling; do not replace it with a background watcher or a duplicate CI dispatch.

For Symphony, `local_gate` is the complete installed Gate entry and `github_api` is the designated publication channel. Read its source-bound status before publication and preserve its host-owned receipt. Interactive work uses the installed approved host described in `.harness-gate/QUALITY.md`; a bare `tools/gate.py verify` without trusted inputs is not equivalent. Installation instructions are not permission to bootstrap or redeploy trusted policy during a feature task.

### Failure recovery and timing evidence

- Classify the failed stage from its retained logs: implementation/test failure, measurement incompatibility, deterministic environment fault, or transient transport failure. Keep confirmed causes separate from hypotheses. Preserve the original task, source, evidence and cumulative budgets.
- Before rerunning an expensive stage, record what changed and the machine-checkable recovery condition. A deterministic failure requires changed prerequisites and checked readiness; another attempt alone is not recovery. For a transient failure, use bounded recovery allowed by the task/controller, check for an existing attempt and preserve the failed attempt. Do not overwrite receipts or restart the entire pipeline blindly.
- For a required host repair, record the bounded change, postcondition and resume stage. Do not modify trusted tools from an agent workspace. A recovery API acknowledgement means accepted, not started; only an observed session establishes startup.
- Retain stage start/end times, source identity, outcome, command/run identity, failure cause and evidence paths in the task's existing evidence location. Reuse host `timings.jsonl` and publication receipts instead of inventing a parallel authoritative status file. Record manual-stage boundaries as they happen; label retrospective estimates. Account for overlapping work once and distinguish execution, waiting and rework.
- A checklist entry is not evidence. Resolve stages from exact-source reports and receipts on resume. Never infer PASS from an old conversation summary, file timestamp, capture directory or successful compilation alone.
