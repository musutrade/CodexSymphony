# 首个日常可用版本：个人全自动开发平台

> V10.3 · 2026-09-15 · 已确认的 V1 产品与验收契约，尚未实现

本文是 V1 使用流程的权威定义。[综合方案](../Personal_AI_Software_Factory_综合方案.md)的 0a 是内部实现里程碑，完成到 PR 不代表本版本交付。
本文要求按依赖分步实施，不把所有能力反向变成第一条 PR 的前置条件。后期通用框架仍见非规范性演进目录。

## 1. 使用入口与正常路径

用户在工作时可以从电脑网页录入需求，也可以使用手机网页；Agent 整理的 Markdown/结构化草稿可以粘贴或导入同一需求入口。
首版不要求任意聊天应用自动同步，导入内容只能形成 Draft；记录来源，不将 Agent 草稿视为用户授权。
自然语言入口由平台生成目标、范围、验收标准和验证计划草稿，用户修改并确认后执行。不强迫用户手填所有结构化字段。

代码变更正常路径：提出需求 → 必要拆分 → 用户评审 → 自动编码 → 受信验证 → PR → CI → 有限修复 → 合并 → 验收完成；仅验证项按第 3 节完成，无需制造代码变更或 PR。
电脑和手机操作同一套持久化需求与队列，不是两套流程。关闭电脑、锁屏或断网不影响后台执行。
单条小需求直接评审入队；大需求使用第 2 节的整组评审，不增加例行人工检查点。

## 2. 大需求、子需求与整组评审

父需求记录整体目标、范围及带 ID 的整体验收 AC；可执行子需求记录 parent_id、kind、顺序、depends_on、目标仓库、独立 AC 和验证计划，kind 只区分 code_change 与 validation_only。
平台可协助生成拆分草稿，用户可修改、删除、重排；只需要父子关系、顺序和依赖，不建设通用 Planner/工作流引擎。
父需求只聚合结果，不占用一个永久的执行槽；队列槽由当前可执行子需求占用，避免父子互等。

整组评审展示父 AC → 子需求/集成项 AC 与验证步骤的覆盖映射；每条必需父 AC 都有承担项，涉及完整功能链的条件由集成项覆盖。映射校验检查遗漏、悬空引用及版本，用户评审语义是否覆盖原目标，不把“存在映射”当作实现已完成。
每个 code_change 在其前置项已合并的基线上可独立验证并安全合并，不依赖尚未执行的后项修复主干。无法这样拆分时合并相关子项或调整顺序，在整组授权前处理。
整组评审界面展示父目标、覆盖映射、全部子需求的精确 revision、kind、顺序/依赖、各仓库策略、允许的修复范围及预算，用户一次确认后原子保存组授权并将子需求入队。
确认前校验无依赖环、无缺失前置项、顺序与依赖相符、覆盖映射完整，且每项有可机器验证的 AC；失败时整组不部分 Ready。
审批记录绑定父/子版本和策略快照。队列到每项时不再次要求 Start、确认修复或人工合并。

运行中允许查看和调整尚未开始的队列。仅重排且不违反依赖不需要重评未变的需求内容，记录队列版本即可。
新增子需求、修改范围/AC/策略或移除必需子需求需评审变化部分，并重新检查父 AC 覆盖；暂停受影响项及其依赖，已完成事实和未受影响授权保留。
不修改正在执行项的输入快照；需修改时先停止保全，对变化版本重新授权，从合适阶段恢复。
调度和编辑用版本校验处理竞态；编辑时已领取的项不能伪装成未开始项。

## 3. 全局串行与完成

所有仓库共用一条严格串行执行队列。当前项达到下表对应完成条件后才开始下一项；Agent 退出、PR 创建、CI 等待及已授权修复均不释放队列。

| kind | 完成条件 |
|---|---|
| code_change | 变更及必要关联修复 PR 已确认合并，适用的子项验收通过 |
| validation_only | 对绑定的精确仓库版本完成全部必需验证；通过时无需编码 Run、新提交或 PR。若产生关联修复，先完成修复 PR 的交付，再对更新的精确版本完成该项全部必需验收 |

前项阻塞时后项等待，不自动跳过依赖；当前项仍可按第 4、5 节自动恢复。手机与电脑的暂停、继续、取消及队列释放例外统一引用主规格第 4.4、6 章，不另设控制语义。取消不冒充 Done，也不能让依赖该项的任务自动通过。
恢复沿用原需求和保存的工作，只在需编码时创建新的执行 Run；不要求为普通失败重新开需求。

同仓后继基线包含依赖项的已合并提交；不同仓库的依赖通过对应版本/产物和验证计划确认，不假设 Git 祖先关系跨仓成立。
每个 code_change 选择一个已登记仓库；validation_only 可验证多个已授权仓库的版本组合，其可修复仓库及范围在首次整组评审中明确。每个关联修复 PR 只修改一个仓库，多个修复仍全局串行；不承诺跨仓原子提交或整体回滚。

全部必需子需求完成且整体集成验收通过后，父需求才 Done；集成验收可作为最后一个队列项，纳入首次整组评审。
集成项绑定各仓库实际版本，验证完整功能链；只执行既有检查时用 validation_only。只合并各子 PR、不跑整体验收不构成父需求完成；集成失败的修复属于当前项第 5 节的关联执行，不创建一个必须等当前项完成才能运行的后继修复子项。

## 4. 澄清、自动恢复与预算

普通澄清在原任务中提问，手机或电脑回答后继续，不要求重新建需求；业务问题、过期 Run 和有效回答的处理统一引用主规格第 8.1 节。用户隔夜或下班后回答仍有效的业务问题时，从原工作恢复，无需先恢复旧 Run 再重复提问；回答若改变范围、AC 或权限则进入变化部分评审。
阻塞详情沿用主规格的六问，显示已保存工作、平台尝试、需用户决定事项和恢复位置。
已授权的网络临时故障、GitHub 限流和 CI 基础设施故障由平台退避恢复；遵守 Retry-After，设置阶段时限，等待不调用编码模型。
未知根因、持续故障、授权扩大、安全失败或预算耗尽才请求用户处理；模型不得通过猜测根因自动扩大权限。

0a 的一次代码修复仅是内部里程碑限制。V1 默认每个可执行项最多 3 次自动代码修复，本地验证/CI/Review、合并后和集成失败的关联修复共用该项计数；已有子项的完成事实不因集成项修复而重写。
整组审批展示父组总上限，默认等于已批准可执行项的预算之和；新增项目或增加预算需明确授权。跨 Run 的已用量、在途预留、项/组上限及拆分/恢复的归属统一引用主规格第 15 章，不以创建新 Run、修复 PR 或新 revision 获得新预算。
普通基础设施重试不消耗代码修复次数，但有独立次数/时限；模型与时间预算及人工等待的计量也按主规格第 15 章执行。
同一输入、环境、命令及失败反复出现且无新进展时提前停止；新代码或环境证据可支持再次验证，但不能绕过总预算。
预算预留与重复事件的处理沿用主规格第 15 章，不因此要求完整 RepairAttempt 框架。

## 5. 平台负责自动合并与业务验收

仓库接入先满足主规格第 11.1 节的自动交付能力检查。PR head、测试合并提交与实际 merged SHA 的检查映射、合并条件、未知结果对账及合并后验证统一引用第 11.2 节，日常版本不另行推导通过条件。只有 PR 触发 CI 的仓库按已评审的能力与验证计划处理，不等待不会产生的合并后 CI，也不把 PR 证据改标成 merged SHA 证据。
正常路径无需人工合并或逐项点击验收。合并后或集成验收失败保留原合并及验证事实，后续队列不启动；这不等于当前项必须等待人工。
已分类、处于当前项获授权仓库/范围内且预算允许的代码失败，由当前项创建关联修复 Run/分支/PR；以实际受影响版本为基线，经同一受信验证和平台交付流程合并，再完成当前适用的子项/整体验收。记录原失败证据、原 PR、修复 PR 及最终验收版本的关联，不复用已合并 PR 冒充新交付，不释放当前队列占用，也不新建绕过依赖或预算的普通需求。
validation_only 失败后的代码修复同样使用上述关联流程，不改变该项原始 kind 或伪造首次验证通过；超出首次授权的仓库、范围、权限或预算才评审变化部分。基础设施失败按第 4 节恢复，未知根因、安全失败及持续无进展按原规则请求用户处理；不自动回滚主干。
三真相与 Gate 职责仍由[架构边界](architecture-boundaries.md)定义；平台不重写 CRAP 等质量语义。

## 6. 手机操作、通知与上线前提

响应式 Web 支持需求录入/草稿评审、整组确认、队列/父子进度、提问回答、恢复、暂停、取消及未开始项重排。
通知优先发送需要行动的事件，并直达原任务；同一阻塞去重，普通进度不反复推送，正常完成可以汇总。
首版一个通知渠道即可，交付失败独立有限重试；通知不是状态真相，待办箱始终可查询，链接不带凭证。
无需 SSH、手工 Git、盯 CI 或另开 Agent 会话才能完成标准恢复操作；确需宿主管理员处理的异常给出明确原因与步骤。

远程上线前按第 6.1 节验收平台用户名、密码登录、源站隔离、会话有效性/撤销、写请求防 CSRF 和请求版本校验。Cloudflare Access 不再承担用户认证；S3 仅保留历史参考，其中 Tunnel 隔离方法可参考并重新验证。页面视觉与响应式验收按 [UI 复用规范](ui-design-system.md)执行。
M2 上线前落实下列实际执行边界，并验证主规格要求的进程停止、受信身份和恢复；可信代码限制保持明确，不把未知隔离能力当作已验证。

| 执行位置 | 日常版本的最低边界 |
|---|---|
| 控制面与 GitHub Broker | 持有平台凭证和状态写权限，经受控接口执行远端动作；不直接执行候选代码 |
| 编码 Run | 采用主规格的可信开发环境方式，普通命令直接执行；控制面/GitHub/签名凭据独立托管，不进入开发环境 |
| 候选/集成验证 | 开发测试在可信环境直接运行；正式验收由独立服务取得精确提交执行并签名；测试只使用获授权的项目测试凭证，不继承控制面凭据 |

基本持久化、备份恢复路径与升级保护覆盖实际日常数据。手机和自动合并不等待完整租约、诊断 Agent、通用资源平台或监控平台建完。

### 6.1 用户名、密码登录

平台自行校验用户名和密码，电脑与手机使用同一账号及业务数据。首版面向个人使用，由部署管理员通过受控初始化命令创建账号，无公开注册和默认密码；首次设置与忘记密码后的重置通过宿主管理命令完成，不要求邮件服务或完整用户管理后台。

- 密码只保存带独立盐的 Argon2id 哈希；明文密码、会话令牌不得写入日志、URL、仓库或 Agent 可读配置。密码输入支持密码管理器和粘贴。
- 登录成功创建随机、不透明的会话令牌，通过 `HttpOnly`、`Secure`、`SameSite=Lax` Cookie 传递；服务端持久化令牌摘要、账号、到期与撤销状态。生产访问必须使用 HTTPS，浏览器不在 localStorage 保存认证令牌。
- 首版会话采用 8 小时绝对有效期，到期重新登录；退出立即撤销当前会话，修改或管理员重置密码撤销该账号全部会话。服务重启不恢复已撤销会话、不延长到期时间。
- 登录失败统一提示“用户名或密码错误”；按账号与可信来源地址限制尝试频率，限制状态在重启后仍有效。仅信任受控代理提供的来源信息。
- 所有业务 API 在后端校验会话；前端路由守卫只负责导航。登录、退出及业务写请求验证预期 Origin，并按 Cookie 会话方案实施 CSRF 保护；未认证访问不能触发业务动作。
- Cloudflare Tunnel 可作为 HTTPS 接入和转发通道，Cloudflare Access JWT、邮箱头及边缘登录状态不授予平台身份。公开业务服务前须通过应用认证验收，并验证源站无未保护入口。2026-09-15 用户已删除 `factory.aglmud.org` 原 Access 认证；无凭据请求不再跳转登录，但返回 502，原实验源站 `127.0.0.1:8790` 无监听。这仅记录当次接入状态，不代表应用登录或远程上线验收通过。
- 会话过期后保留可安全恢复的页面上下文，登录返回原站内页面；未经用户提交的草稿不自动执行，认证重定向不能跳往任意外站。

M2 必须通过以下认证验收；B08 的“远程访问与会话撤销边界有效”包含 AAuth01–AAuth06：

| ID | 场景与通过条件 |
|---|---|
| AAuth01 | 在电脑与手机使用初始化账号登录，看到同一业务数据；无默认密码、无公开注册；未登录直开受保护页面进入登录，直接调用业务 API 返回 401 且不产生副作用 |
| AAuth02 | 错误密码与不存在账号使用相同失败提示；连续失败触发限流；服务重启后限制仍有效，伪造代理来源头不能绕过限制 |
| AAuth03 | Cookie 属性符合上述要求；退出、8 小时到期后旧会话不可重放；修改或重置密码后电脑和手机旧会话均失效，重启不恢复撤销会话 |
| AAuth04 | 跨站登录及业务写请求、缺少或错误 CSRF 证明的写请求被拒绝；合法同站请求通过；日志与浏览器持久化存储不泄露密码或会话令牌 |
| AAuth05 | 无 Cloudflare Access 登录也能通过平台账号正常登录；仅携带伪造或真实 Access 身份头不能访问业务 API；HTTPS 入口可用，源站隔离符合部署要求 |
| AAuth06 | 会话过期能重新登录并回到原站内页面，未提交草稿不自动执行；外站返回地址被拒绝；管理员重置密码后新密码可用、旧密码与旧会话均不可用 |

## 7. 实施顺序

| 里程碑 | 结果 |
|---|---|
| M0：内部 0a | 单仓第一条需求到 PR，然后多仓登记；按现有 A01–A13 验证恢复与交接 |
| M1：需求与队列 | 自然语言/导入草稿、父子拆分、整组评审、顺序和依赖；直接沿用单协调器 |
| M2：远程接续 | 必需认证/隔离、手机同一流程与一个行动通知渠道；补必要日常恢复保护 |
| M3：日常 V1 | CI 有限修复、自动合并、子项验收及父项集成验收；通过 B01–B08 |

按依赖逐项开发，0a 可内部试用，但不以“到 PR”宣布个人全自动平台已交付。

## 8. V1 验收

| ID | 场景与通过条件 |
|---|---|
| B01 | 电脑录入大需求，生成至少 3 个 code_change 及最后 validation_only 集成项；父 AC 覆盖完整且每个代码项可独立安全合并，一次评审后串行完成。覆盖遗漏不允许整组 Ready；最终纯验证无代码差异时无空提交/PR，也能完成父项 |
| B02 | 手机直接提交小需求，以及导入 Agent 草稿；均进入同一队列，草稿未经用户确认不执行 |
| B03 | 用户关电脑，提问等待及旧 Run 均超时后，隔夜用手机回答仍有效且不改范围的业务问题；原工作自动恢复，无需重新建需求、先恢复再重问或 SSH。过期/重复 RPC 回复不能推进旧 Run；已变更的问题要求读取当前版本 |
| B04 | 模拟临时网络/限流、CI 基础设施故障和可修复代码失败；阶段自动恢复，不把等待交给模型。中途重启/新 Run/重复修复事件/新 revision 均不能绕过项及父组的已用量加预留上限，也不重复扣次；超过预算保全并停下 |
| B05 | 子项合并后发生原授权内、预算充足的可修复失败；原项自动产生关联修复 PR 并重新验收，无例行人工批准，后项始终不启动。范围外/安全/耗尽转待办，手机处理后从保存阶段继续；未知合并结果先对账 |
