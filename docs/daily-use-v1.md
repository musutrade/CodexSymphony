# 首个日常可用版本：个人全自动开发平台

> V10.1 · 2026-09-14 · 已确认的 V1 产品与验收契约，尚未实现

本文是 V1 使用流程的权威定义。[综合方案](../Personal_AI_Software_Factory_综合方案.md)的 0a 是内部实现里程碑，完成到 PR 不代表本版本交付。
本文要求按依赖分步实施，不把所有能力反向变成第一条 PR 的前置条件。后期通用框架仍见非规范性演进目录。

## 1. 使用入口与正常路径

用户在工作时可以从电脑网页录入需求，也可以使用手机网页；Agent 整理的 Markdown/结构化草稿可以粘贴或导入同一需求入口。
首版不要求任意聊天应用自动同步，导入内容只能形成 Draft；记录来源，不将 Agent 草稿视为用户授权。
自然语言入口由平台生成目标、范围、验收标准和验证计划草稿，用户修改并确认后执行。不强迫用户手填所有结构化字段。

正常路径：提出需求 → 必要拆分 → 用户评审 → 自动编码 → 受信验证 → PR → CI → 有限修复 → 合并 → 验收完成。
电脑和手机操作同一套持久化需求与队列，不是两套流程。关闭电脑、锁屏或断网不影响后台执行。
单条小需求直接评审入队；大需求使用第 2 节的整组评审，不增加例行人工检查点。

## 2. 大需求、子需求与整组评审

父需求记录整体目标、范围及整体验收；可执行子需求记录 parent_id、顺序、depends_on、目标仓库、独立 AC 和验证计划。
平台可协助生成拆分草稿，用户可修改、删除、重排；只需要父子关系、顺序和依赖，不建设通用 Planner/工作流引擎。
父需求只聚合结果，不占用一个永久的执行槽；队列槽由当前可执行子需求占用，避免父子互等。

整组评审界面展示父目标、全部子需求的精确 revision、顺序/依赖、各仓库策略及预算，用户一次确认后原子保存组授权并将子需求入队。
确认前校验无依赖环、无缺失前置项、顺序与依赖相符，且每项有可机器验证的 AC；失败时整组不部分 Ready。
审批记录绑定父/子版本和策略快照。队列到每项时不再次要求 Start、确认修复或人工合并。

运行中允许查看和调整尚未开始的队列。仅重排且不违反依赖不需要重评未变的需求内容，记录队列版本即可。
新增子需求、修改范围/AC/策略或移除必需子需求需评审变化部分；暂停受影响项及其依赖，已完成事实和未受影响授权保留。
不修改正在执行项的输入快照；需修改时先停止保全，对变化版本重新授权，从合适阶段恢复。
调度和编辑用版本校验处理竞态；编辑时已领取的项不能伪装成未开始项。

## 3. 全局串行与完成

所有仓库共用一条严格串行执行队列。当前子需求完成合并及适用验收后，才开始下一项；Agent 退出、PR 创建或 CI 等待均不释放队列。
前项阻塞时后项等待，不自动跳过依赖。用户可暂停或取消；取消不冒充 Done，也不能让依赖该项的任务自动通过。
恢复沿用原需求和保存的工作，只在需编码时创建新的执行 Run；不要求为普通失败重新开需求。

同仓后继基线包含依赖项的已合并提交；不同仓库的依赖通过对应版本/产物和验证计划确认，不假设 Git 祖先关系跨仓成立。
首版允许子需求各自选择一个已登记仓库；单个子需求不跨仓原子提交，不承诺跨仓整体回滚。

全部必需子需求完成且整体集成验收通过后，父需求才 Done；集成验收可作为最后一个队列项，纳入首次整组评审。
集成项绑定各仓库实际版本，验证完整功能链。只合并各子 PR、不跑整体验收不构成父需求完成。

## 4. 澄清、自动恢复与预算

普通澄清在原任务中提问，手机或电脑回答后继续，不要求重新建需求；回答若改变范围、AC 或权限则进入变化部分评审。
阻塞详情沿用主规格的六问，显示已保存工作、平台尝试、需用户决定事项和恢复位置。
已授权的网络临时故障、GitHub 限流和 CI 基础设施故障由平台退避恢复；遵守 Retry-After，设置阶段时限，等待不调用编码模型。
未知根因、持续故障、授权扩大、安全失败或预算耗尽才请求用户处理；模型不得通过猜测根因自动扩大权限。

0a 的一次代码修复仅是内部里程碑限制。V1 默认每个可执行需求最多 3 次自动代码修复，本地验证/CI/Review 共用计数。
整组审批展示父组总上限，默认等于已批准可执行项的预算之和；新增项目或增加预算需明确授权，拆分/恢复不清零历史消耗。
普通基础设施重试不消耗代码修复次数，但有独立次数/时限；模型调用和总耗时另有固定上限。
同一输入、环境、命令及失败反复出现且无新进展时提前停止；新代码或环境证据可支持再次验证，但不能绕过总预算。
预算预留与修复意图原子保存，重复事件不重复扣次或创建 Run；不因此要求完整 RepairAttempt 框架。

## 5. 平台负责自动合并与业务验收

平台观察精确 repo/PR/head 的 required checks；缺失、失败或不适用性未经确认的 skipped 不能当作通过。
合并前核对受信验证与适用 AC、必要 review 条件，以及没有在途写入/修复/交接；用 expected head SHA 调用 merge。
head 变化失效旧条件；未知合并结果先查 GitHub，不重复编码或盲目再次合并。
合并后确认实际 merged SHA 的必需 CI，并运行确有合并后语义的验收；不默认每条 AC 全量重复两次，也不沿用旧 SHA 冒充新证据。
正常路径无需人工合并或逐项点击验收。合并后验收失败保留事实并阻塞，提出恢复/修复方案；不自动回滚主干。
三真相与 Gate 职责仍由[架构边界](architecture-boundaries.md)定义；平台不重写 CRAP 等质量语义。

## 6. 手机操作、通知与上线前提

响应式 Web 支持需求录入/草稿评审、整组确认、队列/父子进度、提问回答、恢复、暂停、取消及未开始项重排。
通知优先发送需要行动的事件，并直达原任务；同一阻塞去重，普通进度不反复推送，正常完成可以汇总。
首版一个通知渠道即可，交付失败独立有限重试；通知不是状态真相，待办箱始终可查询，链接不带凭证。
无需 SSH、手工 Git、盯 CI 或另开 Agent 会话才能完成标准恢复操作；确需宿主管理员处理的异常给出明确原因与步骤。

远程上线前验证访问认证、源站隔离、会话有效性/撤销、写请求防 CSRF和请求版本校验；可复用 S3 的 Access/Tunnel 结果。
自动执行前落实凭证/执行隔离、受信验证身份、进程停止与恢复；可信代码限制保持明确，不把未知隔离能力当作已验证。
基本持久化、备份恢复路径与升级保护覆盖实际日常数据。手机和自动合并不等待完整租约、诊断 Agent、通用资源平台或监控平台建完。

## 7. 实施顺序

| 里程碑 | 结果 |
|---|---|
| M0：内部 0a | 单仓第一条需求到 PR，然后多仓登记；按现有 A01–A13 验证恢复与交接 |
| M1：需求与队列 | 自然语言/导入草稿、父子拆分、整组评审、顺序和依赖；直接沿用单协调器 |
| M2：远程接续 | 必需认证/隔离、手机同一流程与一个行动通知渠道；补必要日常恢复保护 |
| M3：日常 V1 | CI 有限修复、自动合并、子项验收及父项集成验收；通过 B01–B08 |

按依赖逐项开发，0a 可内部试用，但不以“到 PR”宣布个人全自动平台已交付。

## 8. V1 验收

| ID | 场景与通过条件 |
|---|---|
| B01 | 电脑录入大需求，平台生成至少 3 个子需求及最后集成项；一次评审后按顺序自动完成，无逐项 Start/合并确认 |
| B02 | 手机直接提交小需求，以及导入 Agent 草稿；均进入同一队列，草稿未经用户确认不执行 |
| B03 | 用户关电脑后，仅用手机回答一次不改范围的澄清；恢复原任务，无 SSH/手工 Git/重新创建需求 |
| B04 | 模拟临时网络/限流、CI 基础设施故障和可修复代码失败；阶段自动恢复且预算不重置，不把等待交给模型 |
| B05 | 第一子项阻塞或合并后验收失败，后项不启动；重复事件不多建 Run；手机处理后从已保存阶段继续 |
| B06 | 所有子项通过但集成失败，父项不 Done；修复并通过精确版本的整体验收后才完成 |
| B07 | 变更未开始项、重排/增加依赖及编辑领取竞态正确处理；只重评变化范围，无隐式扩权或取消依赖通过 |
| B08 | head 变化/未知合并结果、手机断线/过期回复、通知失败、凭证隔离与远程访问边界可验证；原始事实和待办不丢失 |

发布记录区分电脑/手机入口、介入原因、阶段耗时与模型消耗；不预设无法证明的零介入率提升。
