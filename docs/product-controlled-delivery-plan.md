# CodexSymphony：环境一致性与受控交付收敛方案

日期：2026-09-24。状态：讨论稿，未启用新能力、未变更队列或授权。

## 1. 目标与事实基线

目标：Agent 在已准备的环境中自主开发；平台保证环境匹配、验证完整、发布有授权、失败可恢复。项目差异通过受审配置和扩展承接。

今天已完成的开发工具链修复提供复用基础，但不代表 Rust 产品已具备全部能力：

| 已有成果 | 产品需要吸收的约束 |
|---|---|
| 单一环境清单，宿主工具复用，启动/运行环境指纹检查 | 每个仓库绑定自己的环境契约；产品负责选择、核验和冻结 |
| 本地完整 Gate 与 CI 复用检查实现；发布入口验证凭据 | 所有产品发布动作必须经过统一准入，不能依靠 Agent 自觉调用 |
| 工具、数据库镜像、资源和测试调度一致 | CI 与开发的同角色环境必须匹配；实际部署进程也须核对 |
| Rust 项目已验证 sccache 固定版本、隔离缓存和可信种子 | 项目可选构建/依赖缓存；平台管理隔离、有效性和可得统计，测试结论独立采集 |
| 开发 Agent 的 Apps/MCP 入口收敛、宿主持有 GitHub 凭据 | 产品的所有 Agent 启动路径都要落实能力和凭据隔离 |
| 工作流模板拼接修复 | 对最终生成配置做语法/语义验证，安装时留存摘要 |
| 服务重启、有效配置与已安装版本的核对 | 安装成功和实际运行版本一致分别验证 |

产品已有基础：Requirement/AgentRun 状态、候选验证、交付/合并与未知结果对账、四类受审 Hooks、按仓库限域的 AppClient。沿用这些模块与全局串行约束。

相关依据：[环境与发布](environment-and-publication.md)、[Hooks 示例](../examples/project-hooks/README.md)、[GitHub 交付](github-delivery-contract.md)、[自动合并](automatic-merge.md)。开发用 Elixir 控制器的补丁不作为 Rust 产品完成证明。

## 2. 平台核心与项目扩展

平台提供受控的扩展调用机制，具体环境探测、验证、权限和交付方式由项目选择的受审 Hooks/适配器提供。可采用固定脚本或现有 Rust 实现的适配，不要求微服务、插件市场或动态加载。

| 部件 | 职责 |
|---|---|
| Agent | 修改工作区、运行开发测试、提交候选材料；不能替换受审扩展或自批验收 |
| 核心协调器 | 授权快照、预算、状态、冻结候选、调用监督、结果身份核对、准入、保全与恢复 |
| 环境扩展 | 核对项目所需工具/服务/限额，返回实际环境事实；不强制某语言或数据库 |
| 验证 Hook | 按项目批准的完整验证方案执行，返回结构化结论、检查项和证据引用 |
| 交付 Hooks/适配器 | 检查目标能力、执行交付、观察状态、对账未知副作用；按需使用外部凭据 |
| 凭据提供方 | 由部署在扩展执行边界供给该操作所需权限；核心配置保存引用和范围，不保存具体厂商私钥字段 |

GitHub App、GitHub PR/Checks、Harness-Gate 和 sccache 都是具体扩展的实现选择，不是平台接入前提。GitHub 适配可以复用现有 AppClient/Broker；local_git 适配不需要 GitHub 凭据或 CI。其他托管平台后续实现同一契约，不在本轮逐一开发。

`my-disposable-bot` 仅是当前 GitHub 部署实例。GitHub 权限/安装/token 处理留在 GitHub 扩展；使用外部可信检查时，发布身份与检查身份按该扩展策略隔离。本地交付没有 token 时，不要求创建空凭据或虚假检查身份。

平台强制的是能力边界和已批准的流程：Agent 无交付写权限；只能调用登记的扩展及限定操作；验证者的执行身份和证据不能由 Agent 伪造；未满足项目声明的必需验证不能进入交付。平台不硬编码具体检查命令、覆盖率阈值、GitHub 分支规则或鉴权方式。

交付扩展获得凭据时，进程不得执行 Agent 可修改的脚本；执行候选代码的验证 Hook 不接触交付/签名秘密。所有 Agent 启动/恢复路径检查 Apps/MCP、宿主登录态、Git credential helper、SSH agent 以及控制目录访问。仅隐藏变量或靠提示词不算隔离。

现有部署面向可信项目代码；凭据和控制状态须有实际进程/文件访问边界。通用恶意代码、多租户隔离不在本轮承诺内。

## 3. 每仓库环境契约

每个仓库维护一份环境定义，平台保存批准版本与摘要，由环境扩展返回实际核验结果。既有 lockfile 继续决定依赖版本，不重复维护另一张版本表。

定义包括项目实际需要的工具版本和摘要、环境角色、资源限额、测试调度、环境变量白名单及受审检查入口。数据库、容器和构建/依赖缓存均按项目需要声明，不是必填能力；平台自身使用 Rust/PostgreSQL 不意味着被开发项目需要它们。

绑定关系：仓库版本 → 批准的环境契约 → 宿主已安装环境配置。任务评审冻结实际选择。默认复用宿主现成工具；不满足时输出差异并阻止启动，由受控安装流程处理，不允许 Agent 自动修改宿主。

不同仓库可以选择不同配置，宿主可并存版本，入口显式选择路径。共享工具只读复用；工作区、数据库数据和临时文件按任务隔离。不能让 A 仓库的配置升级悄悄改变 B 仓库。

核验时点：仓库启用、服务启动、每次执行准备、正式验证启动及发布前。核对实际工具、数据库和限额，并比较有效服务命令/配置/运行版本。运行中配置变化或重启使旧准入失效，重新核验后再执行。

指纹分为：

- 契约身份：批准的声明、检查实现和策略版本。
- 实际环境身份：所选工具和实际依赖/资源/调度配置。
- 运行诊断：主机、目录、进程等记录，避免把无关临时路径当作环境差异。

项目启用 CI 时，开发和 CI 的同一测试角色必须符合相同契约；dev 与 test 的不同限额需显式声明。远端执行环境无法满足契约时明确阻塞，不能拿近似环境冒充一致。

## 4. 状态与扩展事件

保留 Requirement：Draft、Ready、Running、Submitted、Done、Failed、Cancelled；暂停仍是独立控制标志。保留 AgentRun：Created、Running、Succeeded、Failed、Interrupted。

面向用户展示现有记录推导的通用阶段：准备、执行、验证、交付、交付后验收。GitHub 扩展可以提供等待 CI/合并等具体子阶段；本地模式不生成虚假 PR 或合并状态。Submitted 表示适用交付已提交，Done 仍要求适用验收完成。validation_only 直接验证，不造空交付。

现有 after_create、before_run、after_run、before_remove 保持兼容：分别负责准备、执行前准备、保全后的辅助收集和删除前检查。不能把辅助 after_run 的成功解释为验证通过。

新增以下明确扩展点，最终字段/命名由 P0 在统一协议中确定：

| 扩展点 | 责任与结果 |
|---|---|
| 环境核验 | 返回声明与实际差异、环境身份；不匹配阻止执行 |
| validate | 执行项目批准的全部必需检查，返回 pass/fail/unknown 和逐项证据 |
| before_deliver | 可选项目附加检查，失败阻断；不能覆盖 validate 失败 |
| delivery.capability_check | 核对目标、权限和支持的操作；不适用厂商能力无需探测 |
| delivery.submit | 执行指定候选与目标的交付，返回实际事实或 unknown |
| delivery.observe / reconcile | 读取状态、对账响应丢失和取消竞态 |
| post_delivery_validate | 按项目要求验收实际交付版本；不能借用旧候选结果 |
| state_changed | 后续按需求接入的持久状态通知；失败不回滚业务事实 |

GitHub before_publish/before_merge 属于交付适配器内的明确操作边界，可复用同一受审 Hook 调用机制，不成为所有项目必经的顶层状态。Hooks 可以承担真正的完整验证和交付实现，平台无需另一套内置门禁重复执行。

统一调用约定：冻结配置、部署白名单、受审脚本/实现摘要；输入携带任务/revision、候选、环境/策略、invocation/attempt、期限与限定操作；结果携带对应身份、类型明确的状态和证据。平台验证来源与匹配性、必需检查集合完整性，拒绝缺项、过期和非授权调用，不解释某个测试框架内部细节。

外部副作用保存意图后执行；未知结果先对账，重试受预算和幂等策略约束。超时确认派生进程静止。阻断与通知语义在协议中固定，不能由项目把失败伪装成可忽略。新版本/能力不支持明确拒绝；不提供任意状态跳转脚本或第二套调度器。

## 5. 验证与交付流程

1. Agent 声明完成，核心确认静止、保全并固定候选提交/tree。
2. 核心通过受审环境扩展确认实际环境，调用项目选择的 validate Hook。Hook 可以包装现有脚本、测试命令或外部验证服务；Harness-Gate 只是当前项目的一种配置。
3. 验证 Hook 完成批准的完整检查集，核心核对调用身份、候选/环境/策略/实现版本、检查项和原始报告引用，保存结果。可信性由受信调用边界或批准的外部证明提供，不强制每个项目部署签名服务。
4. 必需验证通过后，核心核对授权、暂停/取消和候选当前身份，运行适用 before_deliver；持久化交付意图并调用选定交付适配器。
5. 适配器提交并观察实际交付事实，未知结果通过原操作身份对账。核心不因进程退出为零就推断外部操作完成。
6. 按项目策略执行交付后验证，确认实际交付版本与证据一致后写 Done。

GitHub 项目：适配器处理 PR、精确 CI 来源、head/base、保护规则和实际 merged SHA，继续保留现有检查，不因解耦而放宽。local_git 项目：适配器执行预期基线一致的本地引用更新和对账，按需验证交付版本，无 GitHub App/PR/CI 也能完成。两种路径均复用核心的授权、预算、身份及恢复规则。

项目负责人可以批准不同检查集；执行中的 Agent 不能取消检查或改变通过条件。源码、环境契约/实际身份、相关策略、检查实现及适用基线变化，旧结果失效。未提交内容与固定候选不一致必须被识别。一次运行环境中的可变状态需按方案重验，不把指纹当作永久有效证明。

所有交付路径，包括修复，都经同一批准流程。阶段间携带不可混用的证据引用；验证 Hook 不自行发布，交付 Hook 不能自签验证成功。扩展边界实现可插拔，执行顺序和有效性检查由核心保证。

## 6. 耗时、缓存和失败处理

开发阶段允许局部测试快速反馈；交付前执行项目批准的完整验证 Hook。配置了 CI 的项目保留适用的精确版本验证；无 CI 的项目由受审本地或外部验证实现满足验收。现有项目解耦不删除其既定必要检查。

构建和依赖缓存为项目可选能力，默认可关闭。具体工具、命令及缓存目录由受审项目配置/执行适配提供；平台核心不运行硬编码的 cargo/sccache，也不要求项目为接入平台而更换构建方式。Rust 可以复用今天验证的 Cargo/sccache 配置；其他语言沿用自己的构建与依赖工具；没有构建阶段的项目直接执行批准的检查。

启用缓存时，平台负责作用域、配置/工具/依赖身份、容量与清理策略和写权限边界。采用共享种子时，仅受信路径可更新，任务使用隔离副本；不要求所有工具实现种子机制。缺少缓存或统计能力不阻塞任务，统计不可得标记 unknown/not_applicable。测试结果和适用覆盖率按项目批准方案重新采集，缓存命中不能成为验收证据。

平台从已有执行记录采集排队、准备、验证、发布和 CI 耗时；构建、测试、覆盖率子阶段和命中率仅在执行适配提供时采集，不要求项目修改业务代码来埋点。无编译阶段不伪造编译数据。今天 Rust 项目库重编译约 31.6 秒到 1.84 秒的样本仅是该配置的局部证据。

错误归类为环境不匹配、代码/测试失败、权限失效、协议错误、执行中断、外部结果未知和资源不足。界面显示实际值/期望值、失败阶段、证据和恢复条件。环境及权限错误不自动转为编码修复，不刷新任务预算；未知副作用先对账。

## 7. 实施顺序

| 增量 | 内容 | 退出条件 |
|---|---|---|
| P0 契约收敛 | 核对产品实际入口，确定事件/证据/环境绑定字段；协调现有扩展文档 | 单一协议定义，当前与计划能力清楚，原任务授权不被扩大 |
| P1 环境接入 | 每仓库绑定环境扩展与宿主配置 | 非 Rust、无数据库、无缓存项目可运行；漂移明确阻断 |
| P2 验证扩展与准入 | validate Hook 实现完整验证；核心核对身份/完整性并监督能力边界 | 无有效验证、过期候选或越权操作不能进入交付；无需 Harness-Gate |
| P3 交付扩展 | 统一 capability/submit/observe/reconcile；GitHub 路径适配及操作前 Hooks | 厂商权限与交付语义留在适配器；未知结果可恢复 |
| #105 本地交付 | 从后置调整到本轮，沿用既有 local_git 责任 | 无 GitHub 配置/凭据/请求的真实本地闭环，证明解耦 |
| P4 正式走通 | GitHub 与非 GitHub 小任务，项目验证 Hook 可替换 | 两种实际交付各到 Done；厂商事实和通用状态准确区分 |

顺序：P0 → P1 → P2 → P3 → #105 → P4。状态通知后续接入，不阻塞 P4。模型选择和原日常 V1 业务收尾保留原责任；本方案及 Issue 整理不自动放行队列任务。

## 8. 必须通过的验收

| 场景 | 通过条件 |
|---|---|
| 两仓库环境不同 | 包含非 Rust、无项目数据库且关闭缓存的项目；均可按自身工具链运行，互不升级或覆盖 |
| 工具/镜像/内存/测试并发变化 | 启动或验证明确拒绝，展示期望与实际值 |
| 安装新版本但旧进程仍在运行 | 检测有效服务/进程不匹配，拒绝接单 |
| Agent 跳过测试并声明完成 | 核心调用批准的完整验证 Hook；失败/缺项/未知时没有交付 |
| 验证实现可替换 | 不改核心业务流程，切换受审项目检查脚本；旧证据失效，无 Harness-Gate 依赖 |
| 非 GitHub 交付 | 无 GitHub 配置、凭据或 API 请求，本地项目仍完成交付与验收 |
| PASS 后修改源码或检查策略 | 原证据失效；未提交文件和远端候选不一致也被拒绝 |
| Agent 尝试 Apps/MCP/gh/Git/API 直接写 | 运行环境没有有效写凭据；控制接口拒绝越权请求 |
| 修改 Hook 或候选中的门禁脚本 | 受审身份不匹配，不能自行批准新实现 |
| Hook 超时、子进程残留、取消或重启 | 确认静止与保全；未知副作用对账；不重复发布 |
| 发布/合并响应丢失、head/base 变化 | 读取远端确认；旧证据不能覆盖新版本或触发盲重试 |
| 可选缓存和统计 | 开启/关闭缓存均可完成；缺少命中率不阻塞；适用产物与真实测试正确，报告可得阶段和完整耗时 |
| 旧任务与回退 | 原冻结策略及预算保持，关闭新能力不删除在途操作记录 |
| 产品真实小改动 | GitHub 与 local_git 分别单任务串行验收；使用真实适配器与项目验证 Hook，其他队列保持暂停 |

协议/故障用例使用受控资源；真实 Agent、GitHub、CI 路径单独保留证据。上线前先完成 P1–P3 与 #105 的对应验证，再选择单任务灰度。回退先暂停新领取、确认进程静止并对账远端副作用，使用兼容已有记录的版本，不删除证据或伪造状态。

## 9. 成功标准

可在发布前发现的环境、格式和测试问题不再依赖反复推送发现；Agent 跳过步骤不能跳过产品准入；仓库之间环境差异可配置且可验证；失败可定位到具体阶段并按既有记录恢复。

以真实任务的完整耗时、CI 失败原因、重复提交次数、缓存收益和人工介入次数评估效果。性能目标在取得同类任务基线后确定，不以未经验证的提速比例作为承诺。
