# 自动交付候选

> Deferred: Phase 1 · 非当前规范

## 目标路径

目标为评审后的需求自动通过 PR、CI、有限修复、合并和业务验收。首版仍严格全局顺序，不将等待 CI 当作释放队列的机会。
进入 Current 前明确每个新增状态和 GitHub API 适配，不提前在 0a 创建空表或未使用端点。

## CI、修复与 Review

候选流程：平台观察精确 head 的 required checks；有代码失败证据时启动修复，基础设施故障仅重试相应阶段。
同 repo/PR/head 的重复失败不重复创建尝试。CI/Review/本地修复预算可统一到根需求，但是否需要完整 RepairAttempt 状态机取决于实际并发与来源。
默认上限候选为根需求 3 次，正式提升为 Current 时确定；0a 一次代码修复上限不受此候选影响。
Review 意见可按 thread/意见版本聚合，已处理版本等待确认而不反复唤醒 Agent；自动 reviewer 是独立可选项。
收据式摘要、逐字节引文验证和 formatter 独立候选来源链按真实收益评估，不阻挡首个自动闭环。

## 合并与 Done

拟议合并依据：当前 head 的必需检查、受信验证及适用 AC 满足，必要 review 条件满足，无在途写入/修复/交接；请求携带 expected head，结果未知先查事实。
合并后观察实际 merged SHA 的 CI，并执行确有合并后语义的验收。业务 Done 与 merge 事实分开保存。
不默认每条 AC 合并前后全部重跑两次；按验证对象确定范围，也不拿旧 SHA 绿灯替代最终 SHA 的必需证据。
合并后失败的处理策略单独确定，候选为通知并提出后续修复/revert 建议，不未经授权自动回滚。

## 可后置的优化

- webhook 只在轮询延迟构成问题时作为加速，保留轮询兜底。
- 跨批次证据复用只有在验证耗时有实际瓶颈、provider 能明确身份和适用性后考虑；不确定时完整执行。
- 全量 context digest/NeedsRevalidation 只有在执行中改输入或复杂上下文漂移确有需求时考虑。
- 格式修复可先由现有开发命令处理；平台自产候选和来源链另行评估。

后续阶段的验收将从真实失败、head 变化、重复修复与未知合并结果推导，不整体搬回 V9 故障矩阵。
