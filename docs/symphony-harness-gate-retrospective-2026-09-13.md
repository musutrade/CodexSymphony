# Symphony 开发 Harness-Gate 的运行复盘

复盘日期：2026-09-13。本文是基于本机历史记录的流程建议，不修改综合方案的规范性要求或现有服务配置。

结论：这批任务展示了从 Issue 到 PR/合并的可用交付路径，但也暴露了环境不匹配、恢复依赖人工补丁、交接对账空转和资源保护不足。CodexSymphony 应优先把这些问题变成确定性的调度流程与回归验收，而不是继续增加提示词和放宽运行预算。

## 2. 应保留并落实的做法

1. **编码与交接分开。** 日志反复记录 `Detected external pull request handoff ... ending agent session`；台账的提交摘要明确写 CI pending，由 controller 接管。CodexSymphony 已设计平台负责 push/PR/merge，应保留此边界，使等待 CI 不占模型执行时间。
2. **按依赖拆成有明确验收的任务。** 台账中 GH-111～119、GH-164～170 等系列具有具体范围与前置依赖。继续保留这种任务组织方式，但依赖应结构化，不能只靠正文里的 “Depends on” 和人工添加 ready 标签。当前记录不能单独证明任务粒度与耗时的因果关系。
3. **保留失败和证据身份。** GH-151 区分 candidate SHA 与最终 transfer SHA，并分别记录 hosted 验证；GH-230 明确区分实际发布的 Core 二进制与源码构建。可以作为本项目 VerificationBatch 的接入样例。
4. **明确验收边界。** GH-229/231 的摘要区分 synthetic、skipped、native positive evidence 和未完成的发布验收。保留这种诚实表达，再把它从文本变为可判定的 AC 证据。

这些做法符合本项目“三个真相分离，Gate 只提供验证证据”的既有架构，无需新增一个总状态覆盖其他事实。

## 3. 优先优化的流程

### P0：真实执行环境预检，提前拦住不能开工的任务

**证据：** GH-91 提交摘要记录默认 Cargo target 只读；GH-228 恢复说明记录缺少固定 rustc-dev 输入；GH-230 恢复说明记录 Core v0.3.7 缺少所需 `quality` 能力，以及 Docker 在实际 workspaceWrite 下不可直接访问。后来通过 host 准备、SHA 校验、固定容器队列和 before_run 探针解决。

**建议：** 增加结构化的任务前置能力清单：工具版本/能力、固定依赖、可写构建与临时目录、所需网络、验收执行器。预检必须在与 Agent 相同的沙箱和环境下执行。缺失依赖进入准备/阻塞流程，不启动编码，不消耗代码修复预算。缓存预检时绑定工具、环境和策略身份。

**回归验收：** 注入缺失 rustc-dev、Core 能力不匹配、只读 target、不可访问的验收执行器，模型调用数均为零；依赖补齐后重新预检，保留已有编辑，从未完成阶段继续。

### P0：平台实现 Git 交付能力，消除每个 Agent 自找发布路径

**证据：** 65 条提交摘要中有 56 条包含 `read-only`，这是文本命中数，不是严格的 Git 故障计数。GH-90/117/166 等明确描述复制 Git 元数据后提交；GH-91 经 GitHub Git API 发布，原 checkout HEAD 留在基线；GH-228/229/230 也记录 shell Git 传输失败后用 API 发布。

**建议：** 落实既有 `create_local_commit`、封存 manifest 和平台 outbox；统一记录工作树、artifact commit、远端 head，不能假设它们永远一致。网络发布失败只重试交接。预检验证平台提交工具可用，不以放开 Agent `.git` 或远端凭证为默认解法。

**回归验收：** `.git` 对 Agent 只读时仍能通过平台交付；push 成功但响应丢失后对账恢复，不重复编码、创建 PR 或强推。

### P0：把最低限度磁盘保护前移到 0a

**证据：** 2026-09-09 09:28:34 UTC，生产日志 `.2:14629` 显示 Orchestrator 在 `put_waiting/2` 持久化时收到 `{:error, :enospc}`，触发 MatchError 并退出。日志能证明写入失败，不能证明此前状态一定完整保存，也不能把磁盘满归因于某个特定文件。

**建议：** 综合方案 21.5 已规定低磁盘暂停，23 章却把磁盘不足暂停领取列在 0c；将最小实现明确排入 0a。调度前及运行中检查容量，预留控制面写入空间，持久化失败时阻止后续外部动作。完整自动清理仍可后置。

**回归验收：** 注入持久化 ENOSPC，不能继续推进交接；容量恢复后按已持久化声明和远端事实恢复，不丢失关联、不重复外部写入。

### P0：恢复通过事件执行，保留累计预算和已解决问题

**证据：** 多份 blocked 快照与最终台账的 attempt 数不同。WORKFLOW 中积累了 GH-94/151/228/230 专用授权和恢复段落，多次提醒保留编辑、不要重复已解决探针和下载。

**建议：** 不直接覆盖历史来表达恢复。记录 `RecoveryDecision`：原阻塞、解决证据、适用输入身份、恢复阶段、新增授权预算、已完成验证与剩余 AC。原有消耗保持不可变，明确区分累计消耗和本次授权余额。综合方案第 28 章已有阶段恢复与不重置预算规则，应在 0a 用真实案例验收。

**回归验收：** 模拟 GH-228 补齐依赖，恢复后不再下载同一失败输入；原 attempt/消耗仍可追溯；有产出时只恢复对应验证或交接阶段。

### P1：身份变化触发明确动作，不能无限对账告警

**证据：** GH-208 在 2026-09-10 12:08:30 至 13:37:44 UTC，连续出现 85 条 `pull_request_identity_changed`，约 89 分钟。位置为生产日志 `.2:54720` 起。此日志未带 expected/observed 字段，无法确定是哪个身份字段变化，也不能据此认定发生了误合并。

**建议：** 保留身份守卫；记录期望与实际 repo/PR/head/base。识别属于本平台的合法新 head 时按既有政策失效旧证据、重建验证；不符合允许变化时生成一次可处理阻塞。相同事实只更新计数/时间，停止无效高频动作，等待外部事实变化。

**回归验收：** 外部改变 PR head，旧 SHA 的绿灯不能促成合并；同一冲突只创建一个待办；远端恢复或新证据满足政策后自动继续。

### P1：预算之外增加无进展识别与阶段耗时

**证据：** GH-91 在日志 `.1:47095` 达到 100,024,565 / 100,000,000 token 限制，`.1:65889` 达到约 5 小时运行限制，随后还出现 stall。最终台账记录约 332 分钟、1.053 亿 total tokens。当前 WORKFLOW 把额度设为 5 亿 tokens、10 小时；这些记录不能证明消耗都来自无效工作。

**建议：** 记录准备、编码、验证、CI、交接、人工等待各阶段耗时。对“同一输入、同一命令、同一失败、环境没有变化”的重复执行做失败指纹与次数限制，生成恢复摘要；不把持续输出 token 当作实际进展。按任务类型设软检查点，而非只增大硬上限。

**回归验收：** 确定性依赖缺失反复出现时停止模型重试；有新代码或新环境证据时允许重新验证；输入、缓存输入、输出分别累计。

### P1：日志保留决策，证据进入独立 artifact 存储

**证据：** 现存 5 个生产滚动日志共 593,956 行，其中 587,516 行（约 98.9%）为 `debug: Codex notification:`，多为 delta 类型通知。GH-228 摘要记录将 79,452,501 字节归档拆成 19 份运送，并要求保留 workspace，等待持久 artifact 存储；GH-151 摘要记录 hosted 原始材料保留 30 天。

**建议：** 业务事件单独持久化；delta 调试流独立、限额保留；关键事件带 requirement/run/phase、输入身份、失败码和决策原因。源码仓库存证据 manifest、摘要和内容摘要；大产物进入受控 artifact 存储。先验证上传和下载校验，再允许清理唯一原件，不必在 0a 建完整对象存储平台。

**回归验收：** 不看原始 delta 也能还原一条需求的阶段和介入原因；清理 workspace 后仍能根据 manifest 获取并验证所需证据。

### P1：配置读取异常不能直接击穿调度循环

**证据：** 2026-09-12 07:49～08:06 UTC，生产日志 `.2:111691`、`:111697`、`:111699`、`:111703` 记录 4 次 Orchestrator 因 `WorkflowStore.settings` 的 5000ms 调用超时退出。尚未定位 WorkflowStore 超时根因。

**建议：** 每个调度批次使用已验证、带 revision 的配置快照，配置加载异步进行；超时作为可观察的控制面故障处理。必要策略的新鲜度无法确认时暂停新动作，尤其不能靠旧快照绕过授权撤销。

**回归验收：** 模拟配置读取阻塞，状态和现有任务仍可查询；不重复 dispatch，不丢失已持久化交接，不执行策略身份不明的外部写入。

## 4. 门禁接入必须澄清的一点

多个台账摘要明确写：仓库没有 `.harness-gate/flow.toml` 或 `ci` profile，所以 `harness-gate config check` / `verify --profile ci --all` 为 N/A；同时运行了 Rust/Python 测试及 required CI。这说明 **“用 Symphony 开发了 Harness-Gate”不能直接作为“Harness-Gate 已对自己完成门禁接入”的证据**。

CodexSymphony 0a 已选择 `gate_provider=custom`，此分期合理。必需 AC 的缺失证据不能由 Agent 写 N/A 就通过；N/A 必须来自明确适用性规则。GH-231 的 done 对应任务交付记录，其摘要仍列出生产签名、发布和 P8 后续事项，不能把这个任务的完成扩大为整个发布目标完成。

## 5. 对本项目实施队列的具体建议

- **0a 前置：** 最小磁盘保护、真实环境预检、平台本地提交、按阶段恢复、累计预算与介入事件。保留现有单仓串行和 custom gate 分期。
- **0a 故障演练：** ENOSPC、只读 Git、准备超时、push 成功但响应丢失、依赖补齐后恢复，均采用上述历史案例。
- **Phase 1：** PR 身份变化后的对账动作、无进展识别、分阶段耗时、artifact 留存闭环和配置读取降级。
- **继续后置：** 多仓并发、完整自动清理、复杂成本优化；现有证据不足以支持把这些作为首要投入。

衡量改进时，优先看环境阻塞是否减少模型调用、交接失败是否停止重新编码、人工恢复是否减少、已验收需求的零介入比例是否提高。不要只看 done 数或总 token 下降。
