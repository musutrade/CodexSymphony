## 使用路径

1. 按 [账号与 HTTPS](platform-authentication.md)、[部署边界](m2-deployment.md)接入同一控制面；电脑和手机使用同一账号。
2. 录入需求或导入草稿；草稿不执行。按 [整组评审](group-review.md)核对全部父 AC、子项顺序/依赖、仓库版本、模型、修复范围和项/组预算，一次确认。
3. 按 [队列规则](group-queue.md)串行执行。查看 [手机生命周期](mobile-lifecycle.md)的原任务、保存工作、当前待办和恢复位置；只对变化范围重评。
4. 本地交付按 [local_git](local-delivery.md)核对保护目标和实际提交；GitHub 按 [自动合并](automatic-merge.md)核对检查来源和版本。子项验收后执行完整版本组合的纯验证，纯验证成功不制造空提交。
5. 查看 [诊断](diagnostics-acceptance.md)、[累计预算](budgets.md)和 [扩展恢复](lifecycle-recovery.md)。原件缺失、unknown 用量、权限或范围不足如实保留，不用新建任务重置累计账本。

## 升级与回退

升级先按 [日常恢复](daily-recovery.md)停新领取、保全正在执行的工作、等待进程静止，
对账所有未知外部动作；记录原任务、候选、实际交付、数据库迁移 checksum 和通知账本。
用加密备份在隔离库验证完整性和恢复闸门，再在相同配置/凭据边界下检查兼容性。
SQLx 迁移由产品启动执行，不能修改已应用迁移。实际迁移终点从库和源码读取，工具及策略
从 `environment.lock.json`、锁文件和安装审批读取，不以本页历史版本作为运行参数。

本轮升级检查从 M2 `0024` 和重构后 `0039` 两个独立合成基线开始；执行和比较结果
见 GH-90 迁移原件。新增字段/表不追授旧授权；旧 GitHub 观察变 stale 是要求重新观察，
旧观察与失败证据仍保留。本地交付作用域默认关闭，原修复上限不能自动变成 V1 新上限。

回退前同样停止领取、静止保全和外部对账。只使用已证明能够理解现有冻结输入、恢复决定、
本地交付、模型身份、验证代次和通知记录的版本；否则保持暂停，在隔离环境向前修复或恢复。
本轮不提供通用降级迁移，也不证明旧 M2 二进制能够读取新库。
禁止删表/失败原件、清零余额/预留、把实际合并回写成未发生，或恢复已取消工作。
现场切换步骤与管理员条件沿用 [M2 上线清单](m2-delivery.md)，不能用本地 CI 成功替代。
