# 核心解耦与按任务选择模型：改造需求

状态：待实施契约草案；文档合并不启用开发或生产能力。2026-09-23。
代码核对基线：`4163e4f`（包含 #88 / PR #100、存储范围修正 #101）。
需求总览：[#102](https://github.com/musutrade/CodexSymphony/issues/102)。

## 1. 目标与适用范围

个人开发平台：电脑与手机录入、导入草稿或拆分大需求，评审后严格串行完成开发与验收，减少正常路径人工介入和每个通过验收需求的总消耗。
项目可选择环境依赖、交付方式和任务模型；核心不随数据库工具、代码托管或模型提供方的变化反复修改。
本文件定义产品范围、交付顺序和验收；[扩展协议](extension-protocol.md)唯一规定接口与生命周期语义。Issue 只引用条款、记录实施与证据，不另定义协议。

这是已同意整理的改造需求，不是已上线能力。现有任务继续遵循其冻结授权和已实现契约。主规格中的 GitHub/Codex 固定路径在相应子项合入、验收并显式启用前保持有效；不能仅凭本文绕过原有检查。

## 2. 使用场景

| ID | 场景 | 预期 |
|---|---|---|
| U1 | 电脑生成大需求，拆成简单配置修改、常规功能、复杂修复 | 每个子需求可独立选择模型；一次整组评审，后台串行执行 |
| U2 | 下班后手机查看、回答、暂停和恢复 | 与电脑同一队列；显示真实模型、消耗、交付方式和阻塞原因 |
| U3 | 项目只需本地 Git，不使用 GitHub | 本地交付启用后，不需要 GitHub App/PR/Checks；仍须独立验证和业务验收 |
| U4 | 项目无需数据库，另一项目需要测试数据库 | 只运行各自配置的准备步骤；平台 PostgreSQL 不变成项目依赖 |
| U5 | 可选模型建议服务不可用 | 明确规则和原有执行路径可继续；建议不授权合并、重试或解除保护 |

首版继续接管本人可信代码、依赖本地 Git 和平台 PostgreSQL，不承诺无 Git、任意第三方 Agent 或不可信插件隔离。

## 3. 需求

### RQ1 核心职责与替换边界

核心保留业务与执行状态、全局串行、身份与权限、累计预算、进程静止确认、工作保全、独立验收、外部操作对账和队列释放。
项目脚本负责准备与辅助收尾；交付适配器提供本地/GitHub事实；执行适配器封装 Agent；可选决策适配器提供建议。职责与接口以协议 P1–P7 为准。
复用单协调器和现有记录，不建立插件市场、动态加载系统、事件总线、微服务或每个概念一张表。

### RQ2 项目生命周期 hooks

实现 after_create、before_run、after_run、before_remove；先完成 before_run/after_run 可独立评审的增量，再补创建/删除。
迁出至少一条真实项目依赖准备路径和一条辅助产物收集路径，避免只包一层接口、原硬编码仍决定所有行为。
提供无项目数据库、带可选测试依赖两种配置示例；项目环境故障不得被统一归类为全局存储故障。
核心保全与删除许可不交给可选脚本。钩子不是正式验收或业务 Done 的替代物。

### RQ3 按子需求选择模型

第一增量支持项目默认执行配置和需求显式覆盖。整组评审展示各子项实际 provider/model/effort 与预算，后台按冻结配置执行，不要求每项手工 Start。
先复用 Codex Runtime，在受控环境校验部署可用的模型 ID 与强度组合；Sol/Luna 是用户选型意图，不是硬编码的能力或价格保证。没有可用配置时明确阻塞，不静默换贵模型。
记录实际模型、用量、选择理由与版本。等待 CI、执行测试、状态查询仍使用程序，不调用模型。
自动升级是第二增量：仅沿评审授权的有限升级链，在旧执行组静止且保全后创建新尝试；详见 P5。第一增量不依赖自动升级、Jev 或跨提供方会话迁移。

### RQ4 可选交付

GitHub 仍是已有项目默认；增加 local_git 是后置的独立增量。local_git 项目登记、领取、编码、验证和完成均不得因无 GitHub 凭据被拦截。
本地交付固定可持久访问的提交和验收版本，不生成虚假 PR/CI/合并状态。混合父组以各子项真实交付版本完成依赖与集成验收。
策略与实际运行分别记录。只有对应适配器启用才检查其凭据和远端能力；源码/测试依赖是否需要网络另行按项目配置处理。
不在本轮增加其他代码托管实现、完全无 Git 或通用制品交付系统。

### RQ5 可选辅助决策

沿用 #91 的独立试验，不重复创建 Jev 需求，也不以它为上述交付前置。
平台先用确定性规则和显式配置路由；模型建议只通过 P7 返回。试验必须保留原有授权、脱敏、有限调用和独立评测条件，不因本文自动开始收费调用。

| ID | 可复跑场景与通过条件 | 负责项 |
|---|---|---|
| E01 | 旧配置/历史授权迁移后行为不变；不支持版本和能力在执行前被拒绝；运行中改配置不改变冻结身份 | #103，各实现项回归 |
| E02 | 无 hook 默认路径可执行；两个示例项目只启动声明依赖；真实准备逻辑已迁出核心 | #104 |
| E03 | 首次/恢复/修复分别运行正确 before_run；正常/失败/取消后等待整个执行组静止才 after_run；候选不变 | #104 |
| E04 | 超时、派生进程、重启和结果丢失按 P3 有界收尾；未知非幂等调用不盲目重复；辅助错误不全局闭锁 | #104 |

| E09 | GitHub 路径及混合父组回归，精确版本、关联修复、取消/响应丢失对账保持；纯验证不造空 PR | #105 |
| E10 | 从电脑整组评审到手机接续，严格串行到最终验收；按实际启用能力覆盖，未启用项明确标记 | #89、#90 |

契约/故障测试使用受控资源；实际模型与 GitHub 调用分别标注真实证据或 blocked，不用 mock 冒充实测。项目质量门禁继续适用，不放宽 CRAP、覆盖率或证据身份要求。
每项独立测试自身风险；#90 负责完整组合，不承接所有遗漏的单项恢复测试。新测试结果不覆盖历史失败原件。

## 6. 兼容、迁移与回退

旧任务保持原 GitHub/Codex 策略与累计消耗；新默认仅影响未来评审，冻结任务变更走现有变化评审。平台权限撤销仍优先阻止新动作。
迁移默认保持已有行为，支持关闭新能力；关闭不删除在途调用记录、不将未知改成失败或成功。回退遇到已创建的新模式任务时先停止新领取、保全并采用兼容版本完成/隔离，不能强迫旧二进制解释未知模式。
新字段优先复用既有策略/执行记录；确需迁移时每个实现 PR 提供升级、旧数据测试和回退限制。
存储故障范围已由 #101 修改；遇到新故障先复核该版本并复现，不将旧争锁猜测写成确诊，也不借本轮重写存储系统。

## 7. 衡量效果

按最终验收需求记录实际模型调用/输入缓存输出用量、耗时、重试、升级、人工介入原因和总消耗；不可得数据标记未知。
对比相近任务的完成率和总消耗，避免只比较单次调用价格或把返工成本漏掉。不设未经验证的节省比例，不以新监控平台或在线 A/B 实验为首版前置。
