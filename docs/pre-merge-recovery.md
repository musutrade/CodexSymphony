# 原任务的合并前基线恢复

当候选基于旧目标版本、PR 无法形成 test-merge checkout 时，可在原 Requirement
下明确批准重新生成候选。此入口处理尚未启动合并前验证、尚未发送合并请求的
阻塞交付；不处理结果未知的 Merge，也不将基线冲突伪装成测试失败。

先暂停原任务，确认所有执行已静止，正常关闭旧 PR 并等待平台读取到该 PR
已关闭、未合并的最新观察。旧 PR、候选、验证和原合并动作保留。
不要取消 Requirement、修改数据库、强推旧候选或新建账户重置预算。

受现有登录及 CSRF 保护的
`POST /api/requirements/{id}/pre-merge-recovery` 接收：

| 字段 | 绑定内容 |
| --- | --- |
| `request_id` | 幂等请求标识；同标识不同内容拒绝 |
| `version`、`revision` | 原 Requirement 的当前业务版本和修订 |
| `merge_key` | 原阻塞合并动作 |
| `head` | 旧 PR 的完整候选 SHA |
| `base` | 明确批准的当前目标分支完整 SHA |
| `paths` | 原评审机器可读 repair_scope 内的非空、无重复路径子集 |
| `reason` | 本次恢复原因 |

接受返回 `accepted=true`、`started=false`、新业务版本和 `recovery_id`。
这只是决定已持久化；只有正常解除暂停、观察到执行记录后才表示启动。
`GET` 同一路径返回决定、状态、失败原因及尝试回执。

后台再次核对原组授权、旧 PR 身份、暂停/取消和仓库版本，读取真实目标分支。
目标与批准 SHA 不同就阻止准备；不会自行采用新的目标。准备最多尝试三次，
每次保留结果；进程中断或准入变化导致三次尝试均未形成结果时，也会在重试期限后持久化为 blocked。准备失败且尚未生成关联修复时，可用新的请求标识及当前版本
重新明确决定；旧决定和失败不覆盖。PR 观察过期、重开或合并时，不准入修复
及替代交付，需先由正常观察流程恢复有效事实。

准备成功后，使用现有原项关联修复流程冻结目标源码、预留资源、生成及验证
新候选，再形成替代交付。只有新候选验证成功进入交付时才关联旧交付的替代
记录。原任务、父组、已用量、未知预留及所有失败记录不变；额度不足须走原
账户的显式扩额与恢复流程。本入口不修改额度，也不代表任务 Done。

迁移 `0041_pre_merge_recovery.sql` 只增加恢复决定表及引用，不改历史任务或
账本。仍有恢复决定或关联修复在途时，不应降级到不理解此准入约束的二进制。
开发和发布遵循 [AGENTS.md](../AGENTS.md)，材料退出按
[当前保留策略](quality/evidence-retention.md) 执行。

当前实现的自动化用例覆盖原账户不变、幂等冲突、越界路径、旧版本、PR 重开
及观察过期、目标漂移、有限准备重试和旧候选保全。GH-90 已在原 Requirement 5
实测关闭冲突 PR #16、批准当前基线、生成新候选并受保护合并 PR #17；原账户
和失败保持。实际合并后预设契约失败已触发，下一次关联修复因原额度不足停止，
B05/B06 完整闭环仍未完成。见[真实恢复记录](quality/gh90/b05-premerge-recovery.json)。
本入口也不等于所有新任务均已具备首次调用前的远端基线检查。

## 关联修复的预算停止恢复

`budget group-increase` 只增加原账户额度，不解除已有的关联修复阻塞。
在原任务暂停、执行静止后，宿主可调用
`codexsymphony-server budget repair-recheck --stdin-json`，明确提交
`request_id`、`requirement_id`、当前 Requirement `version`、`failure_id`、
当前 `budget_version` 与原增额的 `authorization_request_id`。

入口只接受预算不足这一种阻塞，要求该原账户确有失败发生后留存的正数增额，
且仍是当前预算授权；不接受其他项的授权、零增额、过期版本或其他故障。
同一失败和增额只能接受一次恢复决定，同请求重放不再次改变状态。
原失败、额度、已用量、未知预留和修复次数全部保留。成功仅将原失败重新置为
待调度，正常解除暂停后仍须通过既有范围、修复次数及项/父组预算准入；CLI
退出成功不代表模型已启动或验收完成。
