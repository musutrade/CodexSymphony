# 需求累计额度与调用结算（0a）

首次 Ready 在同一评审事务中冻结 token、turn、模型工作秒数。需求的全部
Revision 和初始／恢复／修复 Run 都使用 `requirement_id` 的唯一额度账户。
重新评审、策略更新和恢复不能刷新这份额度。升级迁移从已有最早评审建立
初始授权；没有可用快照的旧数据保持不可调用，不能自动猜测额度。

Repository 的可选 `model` 字段通过现有配置 API 保存，领取时从评审快照
复制到 Run。省略它可保留旧的需求管理流程，但不能授权模型调用。没有默认
模型、fallback 或价格推算；修改配置不改变已有 Run 的模型。

## 模型适配器必须遵守的调用边界

`budget_store::reserve` 是平台内部接口，调用方提供精确 RunKey、turn ID、
用途（coding / repair / summary）及一次调用的保守 token/工作秒数预留。
turn 预留必须为 1。事务复核暂停、撤销、冷启动屏障、存储许可、Run 身份、
模型配置与绝对寿命，检查账户已用及所有在途额度，然后持久化调用意图。
只有返回 `Reserved` 才能发起对应调用；`Existing` 表示旧意图需要查询对账，
不能重发。重复标识携带不同参数会失败。数据库异常同样不能发起调用。

Runtime 的协议解析和实际模型发送仍由后续 Issue 接入。本接口不启用调度器，
也不授权自动代码修复；repair 只是用量用途，修复调度仍须独立满足 12.2 的
根需求一次修复 ordinal 与 Run 意图约束。额度增加和准备重试记录没有修改
代码修复次数的字段或操作。

`settle` 接收适配器规范化后的**单 turn 累计值**，不是消息增量，也不能直接
将 thread/Run 历史总数当作该 turn 用量。RunKey + turn + event ID 绑定原始
事件；input、cached、output、模型工作秒数各自取累计高水位，重复和乱序
事件不能扣两次或减少消耗。cached 是 input 的子集，不另加到 token 总数。
实际 Runtime 接入时须用其锁定协议将总累计值转成对应 turn 的累计值，不能
猜测缺失字段。

未知值保存为 null。结果未完成或 input/output/模型时间不完整时，每个维度
至少保留原预留，观察到超出预留的用量则扩大占用。完成信号和最终用量可以
分开到达；均齐备后用实际替换预留，不将二者相加。cached 未知仍保持 null。
旧 Run 在退出、暂停或重启后到达的用量仍可结算，但不能恢复该 Run 执行。
所有原始用量事件、授权理由和增量保留；不保存虚构金额。

额度不足或运行中观测到耗尽会持久化 `budget_exhausted`，并设置活跃 Run 的
停止／保全意图，由现有 coordinator 停止后代并保全工作区。停止回执不能
清空未知模型调用预留。`increase` 要求显式平台用户授权、原因、幂等 ID 和
账户版本，以追加授权增加额度；不清除用户暂停、不重启已停止进程。

人工、暂停、CI、网络等待通过 `record_waiting` 单独累计，重复报告采用高水位；
这些值不扣模型工作时间。模型工作时间必须由 Runtime 的活动计时提供，可
在 token 未知时单独持续结算。Run 的数据库创建时间始终用于八小时绝对寿命，
coordinator 每次正常 tick 检查到期并停止保全，重启不会刷新该时间。

## 已启用的重试

沿用 preparation_record / preparation_history：首次执行外最多两次自动重试，
30 / 120 秒退避、十分钟 deadline、未知探测不重复启动。准备依赖、能力、
路径和部署网络故障可在该预算内再次固定探测；授权、身份、存储、额度、
协议以及未知错误阻止自动重试。原错误、退出码、证据、总次数、下次时间
及当时的额度事实一起保存。显式恢复可重授一组基础设施重试，保留旧历史。

验证、交接、清理仍未启用，不预建记录；后续按现有 Retry 机制接入各自阶段，
不得借基础设施重试重新启动编码或增加代码修复上限。以上均无模型轮询。
